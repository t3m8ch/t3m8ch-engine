# Жизненный цикл окна

## Цель

Понять, как `winit` 0.30.13 передаёт управление приложению, в какой фазе создаётся окно и какие события описывают его состояние до завершения процесса.

Наблюдаемый результат этапа: `cargo run -p game` открывает на macOS одно пустое отзывчивое окно `t3m8ch engine`; изменение размера, сворачивание, восстановление и закрытие отражаются в логах, а запрос закрытия завершает процесс без panic.

## Исходная модель

Модель автора до реализации отдельно не фиксировалась. Поэтому здесь нельзя честно приписать автору конкретные исходные предположения. Проверялись вопросы из Issue #1: кто управляет event loop, когда допустимо создать окно, где живёт состояние между callbacks и как события `winit` соотносятся с действиями пользователя.

## Результат

Создан Cargo workspace с crates `engine` и `game`; `rust-toolchain.toml` выбирает stable Rust. Исполняемый crate `game` напрямую владеет event loop, состоянием приложения и обработкой событий. Crate `engine` пока не получил искусственного публичного API.

Для воспроизведения:

```console
cargo run -p game
```

После запуска нужно изменить размер окна, свернуть и восстановить его, затем нажать кнопку закрытия. Логи показывают создание окна, resize, смену occlusion и корректное завершение event loop.

## Поток данных

1. `main` устанавливает форматирующий subscriber `tracing`.
2. `EventLoop::new` создаёт платформенный event loop. `main` передаёт его в `run_app` вместе с изменяемым `Application`.
3. `run_app` занимает вызывающий поток и вызывает методы `ApplicationHandler`. Он возвращает `Result` только после `ActiveEventLoop::exit` или ошибки event loop; обычное выполнение `main` до этого не продолжается.
4. Первый `resumed` получает `ActiveEventLoop`. Только в этом callback создаётся `Window`, после чего оно сохраняется в `Application.window`.
5. `winit` преобразует платформенные сообщения окна в `WindowEvent` и вызывает `window_event`. Обработчик принимает события только от сохранённого `WindowId`.
6. `Resized` сообщает физический размер клиентской области. Нулевая ширина или высота логируется отдельно как минимизированная или недоступная для вывода область.
7. `Occluded(true)` означает, что окно полностью скрыто; `Occluded(false)` — снова видно.
8. `CloseRequested` логируется и вызывает `ActiveEventLoop::exit`. Затем приходит `exiting`, `run_app` возвращается и `main` завершается.

Наблюдённый на macOS порядок был таким:

```text
resumed
window created
resized
resized
occluded=false
user resize -> resized
minimize -> occluded=true
restore -> occluded=false
close -> close requested
exiting
```

`Suspended` реализован и логируется, но при обычном сворачивании окна на проверенной macOS не приходил.

## Время жизни ресурсов

`EventLoop` создаётся в `main` и передаётся по значению в `run_app`; во время работы он владеет платформенным циклом событий. `Application` — локальное значение `main`, которое `run_app` изменяемо заимствует на всё время диспетчеризации callbacks.

`Window` создаётся в `resumed` и принадлежит `Application.window: Option<Window>`. Благодаря этому окно и его платформенный ресурс сохраняются между callbacks. После запроса закрытия event loop выходит, `run_app` возвращается, затем уничтожаются `Application` и принадлежащее ему `Window`.

`ActiveEventLoop` существует как заимствованный контекст конкретного callback и нигде не сохраняется. Глобальный tracing subscriber действует до завершения процесса.

## Эксперименты и измерения

На macOS выполнен реальный запуск `cargo run -p game`:

- через System Events подтверждено одно окно с заголовком `t3m8ch engine`;
- окно визуально проверено как пустое и открытое;
- изменение внешнего размера до 900 × 700 points привело к `Resized { width: 1800, height: 1336 }` для физической клиентской области;
- сворачивание и восстановление дали `Occluded(true)` и `Occluded(false)` без panic, зависания, нулевого `Resized` или `Suspended`;
- нажатие системной кнопки закрытия дало `CloseRequested`, затем `exiting`; процесс завершился с кодом 0.

`cargo check --workspace --locked` прошёл на macOS. Та же workspace была проверена внутри Linux-контейнера командой `cargo check --workspace --locked`; сборка завершилась успешно. GitHub Actions workflow запускает эту команду на `ubuntu-latest`. Оконный сценарий на Linux не запускался: контейнер использовался только для проверки сборки и не имел display server.

Постоянные автоматические тесты не добавлены. Наблюдаемое поведение проходит через нативный event loop и окно ОС; выделение отдельного тестового интерфейса только ради моков создало бы запрещённый преждевременный application framework.

## Исправленная модель

Так как исходная модель автора не была записана, персональное изменение понимания ещё требует проверки с автором. Реализация и наблюдения подтверждают следующую рабочую модель:

- `main` создаёт event loop, но после вызова `run_app` порядок выполнения задают callbacks `winit`;
- окно создаётся в `resumed`, где доступен активный платформенный контекст;
- состояние между callbacks хранится не в event loop, а в переданном ему `Application`;
- на проверенной macOS сворачивание окна — это смена occlusion, а не приостановка всего приложения;
- resize сообщает физический размер клиентской области, который может отличаться от размера окна в points.

## Чёрные ящики

- Преобразование событий Cocoa в `WindowEvent` внутри `winit`.
- Причина двух одинаковых начальных `Resized` и гарантии порядка соседних платформенных событий.
- Внутреннее устройство `NSApplication`, run loop macOS и платформенных window handles.
- Фактическое поведение callbacks и оконного backend на Linux/X11: в этом этапе проверена только сборка.

Эти чёрные ящики допустимы: текущий этап использует документированный `ApplicationHandler` и проверяет только наблюдаемый жизненный цикл одного окна.

## Отложенные улучшения

`wgpu`, surface, отрисовка, input state, камера, `Game` trait, event bus и универсальный application framework не входят в этап. Код останется в `game`, пока не появится конкретная переиспользуемая ответственность для `engine`.

Автоматизация нативного оконного сценария станет оправданной только при появлении стабильного пользовательского интерфейса, который можно проверять без моков внутренних callbacks `winit`.
