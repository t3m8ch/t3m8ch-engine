# Журнал обучения

Журнал фиксирует не только результат разработки, но и изменение понимания устройства движка. Рабочий код без понятной модели происходящего не завершает учебный этап.

## Единица работы

- Один **учебный этап** начинается с GitHub Issue и реализуется в отдельном PR.
- Один **учебный подэтап** заканчивается содержательным commit, после которого проект собирается и заявленный промежуточный сценарий работает.
- Учебная запись создаётся в том же PR по пути `docs/learning/NNNN-<stage>.md`.
- Следующий этап не реализуется заранее.

## Роли

Автор проекта самостоятельно пишет Rust, WGSL и build-конфигурацию. AI может исследовать документацию, объяснять понятия, предлагать эксперименты, уточнять постановку и делать review. Готовую реализацию или изменение исходного кода AI выполняет только по прямому запросу.

AI может самостоятельно поддерживать проектную и учебную документацию, если она отражает уже согласованные решения и наблюдённые результаты. Он не должен приписывать автору непроведённые эксперименты или неполученное понимание.

## Шаблон учебной записи

```md
# <Название этапа>

## Цель

Какой вопрос исследуется и какой наблюдаемый результат должен появиться.

## Исходная модель

Как автор представлял работу системы до реализации. Какие предположения требуют проверки.

## Результат

Что работает после завершения этапа. Как воспроизвести результат.

## Поток данных

Как управление и данные проходят через добавленную часть системы.

## Время жизни ресурсов

Кто создаёт, хранит, использует и уничтожает значимые CPU- и GPU-ресурсы.

## Эксперименты и измерения

Какие сценарии запускались, чем измерялись и что наблюдалось.

## Исправленная модель

Какие исходные предположения оказались неверными или неполными.

## Чёрные ящики

Что пока используется без полного понимания и почему это допустимо на текущем этапе.

## Отложенные улучшения

Какие идеи сознательно не вошли в этап и какое наблюдение могло бы сделать их актуальными.
```

Раздел не заполняется выдуманным содержанием. Если измерения не имеют смысла на конкретном этапе, это указывается одной строкой с причиной.

## Исследование производительности

Каждое нетривиальное изменение производительности проходит один цикл:

1. Сформулировать проверяемую гипотезу.
2. Выбрать воспроизводимую сцену и метрику.
3. Снять baseline в release-сборке.
4. Найти bottleneck подходящим профилировщиком.
5. Изменить одну существенную переменную.
6. Повторить измерение в тех же условиях.
7. Сравнить результат и проверить побочные эффекты.
8. Записать выигрыш и цену дополнительной сложности.

Один случайный FPS, измерение debug-сборки и ускорение без установленного bottleneck не считаются доказательством.

## Условия merge

- Сценарий из Issue воспроизводится.
- Изменение вручную запущено на macOS.
- Linux-сборка проходит; значимые платформенные этапы дополнительно запускаются на Linux.
- Каждый commit оставляет проект в работающем состоянии.
- В PR нет реализации будущего этапа.
- Каждый новый слой отвечает на уже существующую потребность.
- Учебная запись содержит только реально проверенные утверждения.
- Автор может объяснить поток данных без чтения реализации.
- Review не обнаружил ошибку, делающую зафиксированную модель ложной.
